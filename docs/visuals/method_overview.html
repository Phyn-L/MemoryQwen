MemoryQwen 方法结构总览

Qwen3 冻结主干 + LoRA + M 个与问题无关的 memory token；四个训练目标、两条评测路径、一个 ON/OFF A/B

01一句话：把 context 压进 M 个槽，之后所有问题只读这 M 个槽

一段 context（≤1024 token）连同 M 个可学习的 memory token 一起送进冻结的 Qwen3-1.7B（只挂 LoRA）。 前向结束后只保留 memory 位置上的 per-layer hidden state 与 KV cache，context 本身不再进入后续计算。 于是：

  • 问题期只看到 [question (+readout) + answer] 与 memory 前缀 —— memory 必须在看不见 context 的情况下把答案所需的证据装进去；
  • 同一个 memory 前缀对同一段 context 的所有问题复用一次（KV cache 只算一次），这就是「问题无关、可缓存」的含义；
  • memory 的空间是 M × 2048，相对 1024 token 的 context 就是 64:1 的压缩（A/B 配置 ctx=1024 / M=16）。

关键点：没有任何一行能看见 context（除 memory 行和 context 行自己）。所以「答案对不对」这件事完全由那 M 个槽承载，这就是这个方法的全部赌注。padding 的 key 一律屏蔽；被完全屏蔽的行用 finfo.min 而不是 -inf，避免 NaN。

压缩：一条 context → M 个槽

1024 token 的 context（冻结 embedding 后一次性用完）
M=16 个槽 × 2048 维 → 之后所有计算只看这一段（64:1）

ctx=512/M=16 是 32:1，ctx=1024/M=8 是 128:1。压缩比变了，「同一份评测上能不能答对」的难度就变了 —— 所以 A/B 里 ctx 与 M 必须两臂一致，只动开关。

05四个训练目标：各自在训什么、梯度给谁

损失组合（ON 臂的权重）

total = 1.0 · qa_loss            # 唯一直接对应任务的目标
      + 1.0 · reconstruction_loss # memory-only 探针（context_lm，nats/token）
      + 1.0 · ae_loss             # B2：主干当前缀解码器
      + 0.3 · distill_loss        # B1：KL(带 memory ‖ 不带 memory)

OFF 臂：ae_lm_weight=0, distill_weight=0，只剩 qa + 探针
所以 ON/OFF 的 train/loss 绝对值不可比（损失项不同），只能比 val_*。

冻结的 Qwen3 主干（含它自己的 lm_head）永远不更新；QA 的 logits 来自主干，所以 qa_loss 通过 memory/LoRA 起作用。

为什么 AE 的「用主干打分」不算自欺？与探针的区别

探针（context_lm）：query 位于 t−1，逐层 decoder 只吃 memory 槽，看不到任何 context token，也看不到其它层；输出经共享词表头分类成第 t 个 token。 这是「memory 里到底有没有这段文字」的直接测量，但它是个弱读出器（256-d bottleneck + 单层分类）。

AE（B2）：让整只冻结主干带着 memory KV 前缀去 teacher-forced 重建 context（P(t_i | memory, t_<i)）。它比探针强得多（28 层、全词表、真实因果语言模型）， 所以适合当训练信号；但也正因为主干本身很会续写，它的损失下降不等于 memory 变好 —— 这就是为什么我们把两者都留着：AE 训、探针看。

实现上的三个约定

  • 验证 loader shuffle=False，两臂数据顺序一致 → 差异只来自开关；
  • 评测在 每个 rank 都跑并 all-reduce（少一个 rank 会让别人 NCCL 超时）；
  • cadence 用取模，但 should_evaluate() 保证最后一步一定评测 —— 单 epoch 的 run 不能缺终点数字。

步数只由「每卡 batch × 进程数」决定

1 epoch 步数 = ceil(252465 / (batch_size × NUM_PROCESSES))     # 252,465 = all@ctx=1024 的 context 数

batch 8 × 4 进程 = 全局 32 → 7,890 步/epoch      # 设计稿
batch 12 × 8 进程 = 全局 96 → 2,630 步/epoch     # 你现在改成的版本
batch 8 × 8 进程 = 全局 64 → 3,945 步/epoch

训练脚本启动时会打印一行 schedule: steps=… batch=AxB ranks=… warmup=… teacher_forced_every=… autoregressive_every=… checkpoint_every=… log_every=…， 那是最快的"我到底在跑什么"确认方式。改 batch/进程数必须重算 cadence（或在测试里更新期望）。

08已知陷阱（都是真的踩过的）

现象根因现状
ON 臂跑到第一个 validation 之后那一步就崩：Expected to have finished reduction … did not receive grad for rank N: 757 tied 词表头把 W = E @ adapter 按参数 version 缓存，而评测整个在 torch.no_grad() 里、且它前面刚 optimizer.step()， 于是在 no_grad 下重建的「无计算图 W」被写进缓存 → 下一步训练命中它 → adapter 无梯度 → DDP abort（757 = context_lm_head.adapter.weight）。 单进程不会报错，只有多卡 + tied 才撞上。 已修（2838abe）+ 回归测试 tests/test_vocab_head.py
step 500 附近 CUDA out of memory（ctx=1024/M=8/B=12） 两趟全 context 的 28 层前向（编码 + AE）+ QA 分支的 full-vocab logits（B=12 时那个 3.4 GiB 分配）。 最坏形状实测：编码 57G → QA 111G → AE 前向处 OOM。 A/B 形态（B=8/M=16）最坏 128.5/140 GiB，可跑；评测后额外 empty_cache()
显存碎片提示 expandable_segments not supported H200 上的 torch 不支持该 allocator 选项，设了也会被忽略 别指望它救碎片，靠降低峰值 + 评测后释放缓存
bf16 主干 × fp32 训练量报 expected scalar type BFloat16 but found Float accelerate 的 bf16 autocast 会把 fp32 Linear 的结果变回 bf16，再撞上 fp32 的 LayerNorm 所有模块边界包 no_autocast（444bcea + 两个回归测试）
验证集只覆盖 SQuAD v1.1 的前一段 shuffle=False + validation_max_samples 截断（AR 的 autoregressive_max_qa 是全局行数，按 rank 切连续窗口，换卡数不换题集） 两臂一致即可比；要评全量得改采样策略（未做）
