# H200 记忆读取侧 A/B 设计（`ab_h200_on` / `ab_h200_off`）

## 0. 这次要回答什么

六个 reader 开关（A1 绑定词表头 / C2 memory 初始化 + 槽间注意力 / B2 memory 前缀自编码 /
B1 KL 蒸馏 / C3 问题期 resampler）在同一形状、同一预算下，是否真的提高下游 QA。

之前两次 run **都回答不了**这个问题：

| run | 代码 | ctx / M | 全局 batch | epochs | 问题 |
| --- | --- | --- | --- | --- | --- |
| `0rj6x1xc` | 升级前（config 里还有 `contrastive_*`） | 2048 / 64 | 64 | 1 | 与 OFF 臂差 4 倍上下文、4 倍记忆容量 |
| `vry7n1sw` | 升级后，6 开关全关 | 512 / 16 | 96 | 3 | 与 ON 臂的 ctx/M/batch 全不同；ON 臂那次还 OOM 在 step 500 |

所以这次只改开关：两份 config 除 6 个开关 + `checkpoint.output_dir` 外逐字段相同，
由 `tests/test_ab_configs.py` 断言，手改一份忘改另一份会被测试挡住。

## 1. 两臂的唯一差异

| 开关 | ON 臂 | OFF 臂 | 对应 |
| --- | --- | --- | --- |
| `memory.head_mode` | `tied` | `linear` | A1 |

## 2. 形状与预算

* `max_context_tokens: 1024`，`memory_length: 16`（64:1 压缩），`qa_per_context: 4`，
  `train_datasets: all` → 保留 **252,465** 条 context（丢 6,255 条 >1024 token、2,464 条无可用 QA 对）
* 全局 batch **32** = `batch_size: 8` × 4 个进程 → **1 epoch = ceil(252465/32) = 7,890 步**
* 两臂用完全相同的 schedule，每个数字都是对着 7,890 步定的：

| 字段 | 值 | 理由 |
| --- | --- | --- |
| `training.epochs` | 1 | 这次只问"同一预算下开关有没有用"，不做收敛性研究 |
| `scheduler.warmup_steps` | 400 | 约 5% of 7890（上一版 500/3987 = 12.5% 偏长） |
| `evaluation.teacher_forced_every` | 500 | 15 次 + 最后一步 = 16 个点（TF 便宜） |
| `evaluation.autoregressive_every` | 1000 | 7 次 + 最后一步 = 8 个点（AR 解码贵） |
| `checkpoint.save_every_steps` | 2000 | 2000/4000/6000 + 结束时 `last.pt`，约 1.1 GiB/个 |
| `logging.log_every` | 25 | `train/*` 约 316 个点，曲线够密又不撑大 offline wandb |
| `evaluation.validation_max_samples` | 2000 | 与之前几次 run 一致，避免评测子集变成小样本噪声 |
| `evaluation.autoregressive_max_qa` | 128 | 每 rank 解码条数；×rank 数为全局条数，与 OFF 臂旧 run 同量级 |
| `evaluation.max_new_tokens` | 32 | 与 `scripts/test_icl_baseline.py` 的解码预算一致 |

`teacher_forced_every` / `autoregressive_every` 用取模实现，但 `scripts/train.py`
的 `should_evaluate()` 保证**最后一步一定评测**：500 的 cadence 在 7890 步里最后一次
落在 7500（95%），1000 的落在 7000（89%），没有这条规则就会缺终点数字。

**关于步数**：训练脚本第一行会 echo `schedule: steps=... batch=...x... ranks=...`。
如果那行显示的不是 `steps=7890 ranks=32`，说明 batch/进程数和本设计不一致，此时：

* 想用 8 张卡：把两臂 `training.batch_size` 改成 **4**（全局仍是 32、步数仍是 7890）——推荐，墙钟约快一倍；
* 或者保持 `batch_size: 8` 但用 8 个进程（全局 64）→ 1 epoch = 3,945 步，那就把
  warmup 400→200、TF 500→250、AR 1000→500、save 2000→1000、log 25→15 一起减半
  （**两臂同时改**，`tests/test_ab_configs.py` 会检查）。

## 3. 评测口径（两臂相同）

* teacher forcing 是诊断（它会喂 gold 前缀，`f1` 里混了续写能力），**AR 是头条**；
* `max_new_tokens: 32`、`validation_max_samples: 2000`、`autoregressive_max_qa: 128/rank`；
* 指标口径已经是单尺子版本：`em` / `f1` / `rouge_l` + `first_token_em`（`precision` 已删除）；
* `first_token_em` 现在是"token id 或单 token 归一化文本"判定（`aa6cb6c`）。**旧 run 的
  `first_token_em` 是下界**，跨 run 比较会系统性偏低，所以本 A/B 的两臂要在同一份代码上跑。

## 5. 判读规则（先定好，避免事后找理由）

1. **主判据**：`val_autoregressive/{em,f1}` 的**终点**（两臂都在最后一步评过）。
2. **次判据**：`val_autoregressive/first_token_em`（检索信号）、`val_teacher_forced/ppl`
   （LM 侧质量）、`val_teacher_forced/reconstruction_loss`（memory-only 探针，nats/token）。
3. **不要比 `train/loss` 的绝对值**：ON 臂多了 `ae_loss` + `distill_loss` 两项，损失尺度不同；
   只比 `val_*`。
4. **差距 < 0.01-0.02（AR f1/em）不下结论**：这由 `validation_max_samples` 和
   `autoregressive_max_qa` 的噪声量级决定。想看更细就调大这两项重跑。
5. **单点波动不算趋势**：尤其 step 500-1500（warmup 到 400 才结束）。

## 6. 显存：为什么 ON 会在 step 500 附近 OOM，以及为什么这一版不会

`yux7zkun`（ctx=1024 / M=8 / batch 12 / `ae_lm_positions: 0`）在 step 500 死掉，报错在
`accelerator.backward`：

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 3.40 GiB.
GPU 7 ... 140.06 GiB of which 699.56 MiB is free. 132.20 GiB allocated by PyTorch,
5.31 GiB reserved but unallocated
```

`probe_memory_phases.py`（本仓库外，脚本在 `/home/lijie/proj2/xmu/lz/`）把训练步按阶段拆开测峰值，
**最坏形状**（所有序列都顶到上限）实测：

| 阶段 | ON ctx1024 M8 **B=12**（死掉那版） | ON ctx1024 M16 **B=8**（本 A/B） |
| --- | --- | --- |
| encode_context_prefix（28 decoder） | 57.0 G | 39.7 G |
| QA forward（含 full-vocab logits） | 111.3 G | 75.8 G |
| QA loss | 124.1 G | 84.3 G |
| memory-only 探针 | 119.1 G | 81.5 G |
| AE 前缀自编码前向 | **OOM** | 115.8 G |
| AE loss + distill | — | 117.5 G |
| backward（reserved 峰值） | — | **128.5 G** |

结论：

* **step 500 只是"第一个 eval 之后的那一步"**，不是 eval 本身内存高：eval 会留下 5.31 GiB 的
  allocator 碎片，下一步 backward 的 3.4 GiB 单块分配就找不到连续空间。所以 `scripts/train.py`
  现在在评测后调用一次 `torch.cuda.empty_cache()`（只在真正评过的步上），把这个残留还给驱动。
* **真正的开销来自两处**：QA 分支要物化 `[rows, q+a, 151936]` 的 logits（B=12 时约 3.4 GiB，正是
  报错里的那个数）并保留 backward 图；ON 臂又多了一整趟 **AE 前向**（28 层、全 context），
  B=12/ctx=1024 下再要 ~50 G。OFF 臂没有这一趟，所以它在 ctx=512/B=12 下能跑完。
* **本 A/B 的形状在最坏形状下仍有 ~11 G 余量**（128.5 / 140.06 G reserved），而真实 batch 通常远短于
  上限（实测一个真实 batch：ctx 458 token、answer ≤19 token 时，QA loss 之后只有 26.5 G）。
  参考：死掉那版真实运行时的稳态是 114-132 G/卡，按 batch 8 折算约 90-100 G。
* H200 上 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 会打印
  `expandable_segments not supported on this platform`，即**不可用**，别指望它救碎片。
* 想要更大余量：把两臂的 `data.qa_per_context` 一起降到 2（QA 部分大致减半）、`max_answer_tokens`
  降到 64（QA 序列直接砍半），或 `batch_size` 降到 6。不要只改一臂（`tests/test_ab_configs.py` 会挡住）。
* **实测到的失败形状**：`batch_size: 12`（全局 96）时 ON 臂跑到 `2243/2630`（85%）才 OOM
  （`Tried to allocate 4.21 GiB`，卡上只剩 3.57 GiB）。这不是随机抖动 —— 训练集是按长度
  sortish 排序喂的，**最长的一批 context 落在 epoch 后段**，所以那 10-15% 才是显存峰值。
  想在 batch 12 上跑，就得先把 QA 序列压下来（`max_answer_tokens: 64` + `qa_per_context: 2`）。

## 7. 陷阱清单

* `ae_lm_positions: 128` / `distill_positions: 128` 是**采样**位置；改成 `0` 表示**全部位置**，
  会显著变慢甚至爆显存 —— 上一版 ON 尝试（`rmidw6e2`）就是 `ae_lm_positions: 0`，step 500 OOM。
* 两臂 `seed: 42`，数据顺序一致（`shuffle=False` + sortish sampler 每 epoch `set_epoch`），
  所以差异只来自开关。
* 任何 cadence / 形状改动必须两臂同步；`tests/test_ab_configs.py` 会挡住只改一份。它同时把
  第 2 节那张 schedule 表（batch 8 / 4 进程 / 7890 步）钉住了：改了 `training.batch_size`、
  epochs、warmup 或任一 `*_every`，它会以 `('ab_h200_on.yaml', 'training.batch_size', 12, 8)`
  这种形式失败 —— 那是在提醒"cadence 的百分比已经变了，请一起重算并更新测试"，不是代码坏了；
  只改一臂则由 `test_the_arms_differ_only_in_the_six_switches_and_the_output_dir` 挡住。
* `head_mode: tied` 的词表头有一个**只有评测会触发**的坑，已在 `2838abe` 修掉：
  `VocabularyHead.materialized_weight()` 原来会把 `torch.no_grad()` 下 materialise 出来的权重
  （评测整个跑在 no_grad 里，而它前面刚做过 optimizer.step、version 已经变了）按当前 version
  写进缓存，下一步训练 forward 命中它 → adapter 收不到梯度 → DDP 在下一步开头直接 abort：
  `Expected to have finished reduction ... did not receive grad for rank N: 757`
  （757 = `context_lm_head.adapter.weight`）。回归测试在 `tests/test_vocab_head.py` 的
  `test_a_no_grad_materialisation_does_not_poison_the_next_training_step`。单进程不会报错，
  所以只有"多卡 + tied"才会撞上。
* 别把这次的 run 和 `0rj6x1xc` / `vry7n1sw` 混在一张图上做结论：它们的 ctx/M/batch/epochs
  和代码版本都不同，只能当规模参照。

## 8. 崩溃与续跑（resume）

`--resume` 是训练脚本自带的能力，`scripts/train.sh` 会把参数原样透传给 `train.py`：

```bash
# 单臂从某个 checkpoint 继续
bash scripts/train.sh --resume outputs/ab_h200_on/step-1200.pt

# 走 A/B 脚本：按臂自动挑"最新的那个 checkpoint"继续（没有 checkpoint 的臂照常从头跑）
RESUME=1 NUM_PROCESSES=8 bash scripts/run_ab.sh
```

**存了什么**（`utils/checkpoint.py`）：所有 `requires_grad` 的 trainable 张量（memory_tokens、LoRA、
decoders、探针词表头、resampler；冻结主干不存，所以文件只有 ~200 MB 而不是 4 GB）、optimizer、
scheduler（所以 cosine 的学习率从断点继续，而不是重新爬）、`step`、python/torch RNG、
wandb run id（同一个 run 继续记）、以及 **world_size**。

**恢复语义（`281f7b1` 之后）**：按 `step` 推出「从第几个 epoch、跳过多少已消费的 batch」，
并且恢复后**步数预算仍然生效**（到 `total_steps` 就停）。修之前不是这样：epoch 循环从 batch 0
重来、还会在已加载的 step 之上再跑一整个 epoch，等于把 run 拖长一倍。

**三条硬约束**：

1. **rank 数必须一致**。分片方式决定"跳过哪些 batch"，`NUM_PROCESSES` 变了会打印
   `resume: WARNING checkpoint was written with N ranks but this run uses M`，此时跳过的 batch
   不是这个 rank 真正看过的那些（结果仍然能跑，但数据流不再等价）。
2. **形状/目标必须一致**（`memory_length`、`lora_rank`、decoder 宽度、`reconstruction_loss`、
   head 模式……）。不一致时 `load` 直接报错，而不是静默留一部分参数在随机初始化。
3. **checkpoint 落盘节奏**决定最多丢多少：每 `save_every_steps` 写一个 `step-N.pt`，同时刷新
   `last.pt`（硬链接，不占双份空间）；训练正常结束时再写一次 `last.pt`。所以崩溃最多丢
   `save_every_steps` 步（这里 400 步 ≈ 8-10 分钟）。

**checkpoint 到底在哪**（这次顺手修掉的一个坑）：`scripts/train.py::_configure_run_paths` 原来
把配好的 `checkpoint.output_dir` **整个覆盖**成 `outputs/<自动 run 名>`，所以配置里写的
`outputs/ab_h200_on` 从来不存在 —— 每个 run 都散落在 `outputs/Qwen1.7B_<时间戳>/` 里，崩了之后
不但人找不到，`RESUME=1` 也找不到。现在是一次 run 一个子目录、**挂在配置的输出目录下面**：

```
outputs/ab_h200_on/Qwen1.7B_20260917_153958/step-400.pt, step-800.pt, ..., last.pt
outputs/ab_h200_off/Qwen1.7B_20260917_161000/...
```

启动时打印的 `schedule:` 行末尾现在带 `output_dir=...`，`scripts/run_ab.sh` 也会到
`outputs/<arm>/*/` 里挑步数最大的那个 checkpoint。

**A/B 口径提醒**：严格可比要求两臂的"训练进度比例"一致。若一臂从头、另一臂从中途续跑，两臂
实际喂过的样本数就不同，比较时要注明（这也是为什么宁可先解决 OOM 再整轮跑，而不是反复补跑）。
